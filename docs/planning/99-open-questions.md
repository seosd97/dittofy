# 99. Open Questions — 결정 완료

## 개요
기획 리뷰에서 도출된 미결 사항. 모든 항목이 결정 완료됨.

---

## Q1. "양산"의 정확한 의미 ✅

**문제**: "양산"이 두 가지 의미로 혼용됨 (A: 새 프로젝트 생성 / B: 기존 프로젝트에 추가)

**결정**: v1은 A(새 프로젝트 생성)가 기본. B(기존 프로젝트 확장)는 별도 기능으로 만들지 않되, 디자인 스펙 문서가 자연스럽게 B에도 활용될 수 있도록 문서 품질을 확보하는 수준.

---

## Q2. 사용자 피드백 루프 ✅

**문제**: 분석 결과물이 불만족스러울 때의 워크플로우가 미정의

**결정**: 사용자 수동 보정이 공식 워크플로우. `analysis.json`이나 디자인 스펙 문서를 직접 수정 후 `--prompts-only`로 Prompt만 재생성. v1에서 자동 피드백 메커니즘은 제공하지 않음. README에 "결과 확인 → 문서 수정 → Prompt 재생성" 흐름 안내.

---

## Q3. 코드만으로 디자인 에센스를 파악할 수 있는가 ✅

**문제**: Ditto의 근본적 가정이 검증되지 않음

**결정**: v1은 코드 분석 전용으로 진행. M1 완료 시 벤치마크 레포로 분석 품질 수동 평가. 품질 불충분 시 v1.x에서 스크린샷 보조 분석 추가 검토. 기획 문서에 "코드 분석의 한계" 명시.

---

## Q4. 비용 모델 ✅

**문제**: LLM 호출 비용/시간에 대한 예상이 없음

**결정**: 기획에 예상 범위(소규모 $0.5~2, 중규모 $2~8, 대규모 $8~20+)를 참고용으로 명시. `--dry-run`, `--max-files` 같은 비용 관리 기능은 v1에 포함하지 않고 v1 이후 검토. M0에서 실측 후 가이드라인 갱신.

---

## Q5. 레퍼런스 품질에 따른 graceful degradation ✅

**문제**: 분석 항목이 "잘 구조화된 프로젝트" 기준으로 설계됨

**결정**: Phase 1 후 Health Check 수행 (pass/warn/fail). 정보가 부족한 항목은 LLM이 최대한 유추하여 보완하고 confidence level(high/medium/low)로 신뢰도 구분. 아예 분석 불가능한 경우에만 "분석 불가" 표기. 최소 요건: 스타일링 코드가 존재하는 FE 프로젝트.

---

## Q6. 반응형/인터랙션의 구현 단계 배치 ✅

**문제**: 반응형(Step 7)과 인터랙션(Step 8)을 분리할지 통합할지 불확실

**결정**: 분리 유지. 단, 통합/분리 기준을 예시로 명확히 명시.

**컴포넌트 단계에서 함께 구현 (통합):**
- hover/focus/active 상태 스타일 (버튼 색상 변화, 카드 그림자 변화 등)
- disabled 상태 스타일
- 기본 cursor 변경
- focus-visible 아웃라인

**Step 8에서 별도 구현 (분리):**
- 페이지/섹션 진입 애니메이션 (fade-in, slide-up 등)
- 스크롤 기반 애니메이션 (scroll-triggered, parallax)
- 복잡한 트랜지션 (페이지 전환, 모달 열림/닫힘 모션)
- 마이크로인터랙션 (토글 애니메이션, 숫자 카운트업 등)
- 로딩 상태 애니메이션 (스켈레톤, 스피너)

## Q7. Prompt 단계의 범위 기준 ✅

**문제**: "AI Agent 한 세션 분량"이 정량적으로 미정의

**결정**: 정량 가이드라인 — 생성/수정 파일 5~15개, 컴포넌트 10개 이내, Prompt 2,000~5,000 단어. 분할 규칙 — 컴포넌트 10개 초과 시 카테고리별 분할, 페이지 3개 초과 시 페이지별 분할. Agent별 차이는 README에 합치기/나누기 가이드 포함.

---

## Q8. 경쟁/대안 분석 ✅

**문제**: 기존 도구와의 차별점이 문서화되지 않음

**결정**: 00-project-overview.md에 포지셔닝 섹션 추가.

| 대안 | 접근 방식 | Ditto와의 차이 |
|------|----------|-------------|
| v0 (Vercel) | 프롬프트 → UI 코드 생성 | 레퍼런스 분석 없음, 일회성, 양산 불가 |
| screenshot-to-code | 스크린샷 → 1:1 복제 | 에센스 추출이 아닌 복제, 양산 불가 |
| "이 사이트 보고 만들어줘" | 비체계적 구두 지시 | 재현 불가, 정보 누락, 품질 편차 |
| **Ditto** | 코드 분석 → 에센스 추출 → 문서 + Prompt | 양산 가능한 디자인 시스템 문서, 체계적 Prompt |

## Q9. 벤치마크 레포 선정 ✅

**문제**: 품질 검증용 기준 레포가 미선정

**결정**: 기획에서는 선정 기준만 명시, 구체적 레포는 M1 시작 시 선정.

선정 기준:
- 3~5개 레포
- 스타일링 방식 다양성: Tailwind 1개 이상, CSS Modules/SCSS 1개 이상
- 규모 다양성: 소규모(컴포넌트 10개 미만) 1개, 중규모 이상 1개
- 구조화 수준 다양성: 잘 정리된 디자인 시스템 1개, 하드코딩 위주 1개
- 프레임워크 다양성: Next.js 1개 이상, Vite/CRA 1개 이상

## Q10. 문서 생성의 가변성 ✅

**문제**: 7개 문서가 모든 레퍼런스에 동일하게 생성되는 구조가 적절한지 불확실

**결정**: 분석 결과에 따라 동적으로 문서 구성. 해당 없는 문서는 생략 (빈 문서 만들지 않음). 기본 7개에 없더라도 레퍼런스 특성상 필요한 문서가 있으면 추가 생성 허용 (예: `dark-mode-strategy.md`, `form-patterns.md` 등). `00-overview.md`에 생성된 문서 목록과 각 문서의 존재 이유 기재.

## 추가 이슈

### A1. 스타일링 방식 지원 티어 ✅

**문제**: 스타일링 방식별 지원 수준이 미정의

**결정**: 3단계 티어.
- Tier 1 (완전): Tailwind CSS, CSS Variables — 직접 토큰 추출 + LLM 분석
- Tier 2 (부분): CSS Modules, SCSS, Styled Components — LLM 기반 패턴 분석
- Tier 3 (제한): CSS-in-JS 런타임, 기타 — 최선 노력, 한계 명시

### A2. Scaffold + Prompt 하이브리드 전략 ✅

**문제**: 프로젝트 셋업/설정 같은 부분은 Prompt보다 코드 생성(Scaffold)이 더 적합할 수 있음

**결정**: v1은 Prompt Only. v1.x에서 `--scaffold` 옵션 검토 (Step 1~2를 대체하는 역할).

### A3. Pre-analysis Health Check ✅

**문제**: 분석 불가능한 레포에 대해 비용만 소모할 수 있음

**결정**: Q5와 통합. Phase 1 완료 후, Phase 2 진입 전에 Health Check 수행. 체크 항목: FE 프로젝트 확인, 스타일링 파일 존재, 컴포넌트 파일 존재. 결과: pass/warn/fail. fail 시 분석 중단, warn 시 경고 후 계속 진행.
