# 04. Quality Criteria — 품질 기준 & 검증 방법

## 1. 궁극적 품질 기준

> **생성된 Prompt를 AI Coding Agent에게 단계별로 전달했을 때,
> 레퍼런스의 디자인 에센스를 반영한 프로젝트가 구현되는가?**

> 그리고 생성된 디자인 스펙 문서를 기반으로,
> **같은 스타일의 새로운 페이지/컴포넌트를 만들 수 있는가?**

---

## 2. 품질 3계층

### Level 1: 기술적 정확성 (Technical Correctness)
생성된 코드/설정이 에러 없이 동작하는가?

| 검증 항목 | 기준 |
|----------|------|
| 프로젝트 생성 | `npm install` 에러 없음 |
| 개발 서버 | `npm run dev` 에러 없이 페이지 표시 |
| 빌드 | `npm run build` 에러 없음 |
| TypeScript | 타입 에러 없음 |
| 문서 완결성 | 분석된 모든 토큰/컴포넌트/페이지가 문서에 존재 |

### Level 2: 디자인 반영도 (Design Fidelity)
레퍼런스의 디자인 에센스가 결과물에 반영되었는가?

| 체크 항목 | 확인 내용 |
|----------|----------|
| 색상 톤/무드 | 전체적인 색감이 같은 분위기인가 |
| 타이포그래피 성격 | 폰트 느낌, 제목/본문 스케일 대비가 유사한가 |
| 여백 밀도 | 전체적 여유로움/밀집도가 유사한가 |
| 형태(Shape) | 모서리 둥글기 등 형태적 특징이 유사한가 |
| 깊이/그림자 | 깊이감 수준이 유사한가 |
| 모션 성격 | 애니메이션 절제/화려 수준이 유사한가 |
| Do's & Don'ts | 문서에 명시된 규칙이 준수되는가 |

### Level 3: 양산 가능성 (Producibility)
문서를 기반으로 "같은 스타일의 새로운 것"을 만들 수 있는가?

**양산 테스트:**
1. 생성된 design-spec 문서만 AI Agent에게 제공
2. "이 디자인 스타일로 [문서에 없는 새 페이지/컴포넌트]를 만들어줘"
3. 결과물이 기존 스타일과 같은 패밀리에 속하는지 확인

**성공 기준:**
- 새 결과물이 기존 디자인 토큰을 올바르게 사용
- 레이아웃 패턴이 기존과 일관됨
- 전체적인 톤/무드가 일치
- Do's & Don'ts를 준수

---

## 3. 분석 정확도 검증

### 3.1 토큰 추출 정확도
- Precision > 80% (추출한 토큰 중 실제 사용되는 비율)
- Recall > 70% (실제 토큰 중 추출된 비율)
- **에센스 중심이므로 recall보다 precision이 더 중요** — 핵심 토큰 누락만 아니면 OK

### 3.2 컴포넌트 감지 정확도
- 주요 컴포넌트 (디자인에 영향을 주는 것) 90% 이상 감지
- 카테고리 분류 정확도

### 3.3 에센스 정확도 (주관적 평가)
레퍼런스를 아는 사람이 에센스 설명을 읽고 평가:
- "이 설명이 레퍼런스의 느낌을 정확하게 포착했는가?" (1~5점)
- "이 설명만 보고 같은 스타일을 만들 수 있겠는가?" (1~5점)
- "Do's & Don'ts가 적절한가?" (1~5점)
- 목표: 평균 3.5점 이상

### 3.4 벤치마크 레포 선정 가이드
M1 시작 시 아래 기준으로 3~5개 레포를 선정하여 지속 테스트한다.

**선정 기준:**
- 스타일링 방식 다양성: Tailwind 1개 이상, CSS Modules/SCSS 1개 이상
- 규모 다양성: 소규모(컴포넌트 10개 미만) 1개, 중규모 이상 1개
- 구조화 수준 다양성: 잘 정리된 디자인 시스템 1개, 하드코딩 위주 1개
- 프레임워크 다양성: Next.js 1개 이상, Vite/CRA 1개 이상

## 4. 시각적 비교 가이드라인 (v1: 수동)

v1에서는 자동 visual diff를 지원하지 않는다. 수동 비교 방법:

1. 레퍼런스 사이트를 브라우저에서 열기
2. 생성된 프로젝트를 `npm run dev`로 실행
3. 같은 뷰포트 크기에서 나란히 비교
4. 확인 사항:
   - "같은 느낌인가?" (1:1 일치가 아닌 **톤/무드 일치**)
   - "같은 스타일 가족으로 보이는가?"
   - "디자인 원칙이 준수되었는가?"

## 5. 알려진 한계

| 한계 | 영향 | 대응 |
|------|------|------|
| LLM의 주관적 해석 | 실행마다 에센스 분석이 다를 수 있음 | 구조화된 output schema, 낮은 temperature |
| 시각적 검증 불가 (v1) | 렌더링 결과를 자동 확인할 수 없음 | 수동 비교 가이드라인, 향후 visual diff |
| CSS-in-JS 분석 난이도 | 런타임 결정 스타일 파악 어려움 | 코드 패턴 기반 정적 분석 + LLM 추론 |
| 동적 스타일 | JS 로직에 의한 스타일 누락 가능 | 정적 분석 한계 명시 |
| 이미지/일러스트 | 비주얼 에셋 스타일 분석 제한적 | "일러스트 스타일: 플랫, 라인 기반" 수준 서술 |

---

## 6. 향후 자동화 검증 (v1 이후)

- Prompt 실행 자동화 (AI Agent에 순차 전달 → 빌드 성공 확인 → 스크린샷 캡처)
- 스타일 일관성 검증 (생성 프로젝트의 CSS 파싱 → 문서 토큰과 비교)
- Visual Regression (레퍼런스와 생성물 스크린샷을 AI로 비교)
